# ADR — ניהול החלטות ארכיטקטורה

## למה ADR

בשלב [ארכיטקטורה ו-Re-Engineering](sdlc-אגנטי-5-שלבים.md#שלב-3-ארכיטקטורה-ו-re-engineering) מתקבלות החלטות בלתי-הפיכות: לשמר קוד קיים או לבנות מחדש, איזה סטנדרט לאמץ, איך לפתור התנגשות בין שני מקורות ידע ב-[Business Wiki](../00-חזון-ועקרונות/תפיסת-ה-wiki.md). החלטות כאלה **חייבות תיעוד** — אותו עיקרון בדיוק שמנחה את [תיעוד ההחלטות במפעל הבעיות](../01-מפעל-הבעיות/ניהול-משפך-ותיעדוף-דינמי.md), רק בהקשר טכני.

**Architecture Decision Record (ADR)** הוא סטנדרט מקובל בעולם (Michael Nygard, ותבנית **MADR** הנפוצה כיום) לתיעוד החלטה בודדת: ההקשר, האפשרויות שנשקלו, ההחלטה וההשלכות.

## עקרונות

- ADR נשמר **כקובץ MD ליד הקוד/הוויקי**, לא במסמך נפרד — עובר את אותו Code Review וגרסאות Git.
- **ממוספר סדרתית ולעולם לא נמחק.** אם החלטה התהפכה — הקובץ הישן נשאר, מסומן כ"הוחלף על-ידי ADR-00X", והחדש מפנה אליו. זהה לעיקרון "בעיה שנפסלה חוזרת למאגר, לא נמחקת" ב[מפעל הבעיות](../01-מפעל-הבעיות/ניהול-משפך-ותיעדוף-דינמי.md).
- **קצר בכוונה** — עמוד או שניים, בסגנון "פירמידה הפוכה": ההחלטה בראש, הפרטים בהמשך.
- חי בתיקיית `adr/` בתוך ה-Business Wiki של כל מיזם. דוגמה: [כורי-בינה/כור-ביטוח-לאומי/06-business-wiki/ארכיטקטורה/adr](../../כורי-בינה/כור-ביטוח-לאומי/06-business-wiki/ארכיטקטורה/adr).

## מבנה קובץ ADR (MADR מקוצר)

תבנית מלאה למילוי: [06-כלים-ותבניות/adr-תבנית.md](../06-כלים-ותבניות/adr-תבנית.md).

```
# ADR-00X: <כותרת ההחלטה>

סטטוס: מוצע / מאושר / הוחלף על-ידי ADR-00Y
תאריך: YYYY-MM-DD

## הקשר
מה הבעיה/המצב שמחייב החלטה?

## אפשרויות שנשקלו
1. ...
2. ...

## ההחלטה
מה הוחלט, ובקצרה — למה.

## השלכות
מה זה אומר להמשך (חיובי ושלילי גם יחד).
```

## מי מאשר

לפי [Human in the Loop — ממשל](human-in-the-loop-ממשל.md): החלטה טכנית משמעותית עוברת אישור אנושי מפורש — AI מייצר את הטיוטה וממפה את האפשרויות, אך אינו "סוגר" ADR בעצמו.
